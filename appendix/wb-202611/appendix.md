## 2 项目规则文件

对应基准第 1 章 2.2“九栏一览”与第 7 章 2.7“栏 7、8、9：照抄”；补五步中的“生成 Plan 和项目规则文件”。

结论：每轮都要守的规矩写进项目根的 `CODEBUDDY.md`，这一轮做什么仍写在任务书里。两者分工如下：

| | 任务书 | 项目规则文件 |
|---|---|---|
| 管什么 | 这一轮做什么：要证明的一件事、不做清单、验收方式 | 每轮都要守的规矩：目录、只读、端口、检查命令、禁区、提交 |
| 谁写 | 你按九栏写，贴进会话 | 第一轮开工前放进项目根，之后少改 |
| 多久换一次 | 每轮一份 | 跨轮沿用；规矩变了才改，改了记进任务书的迭代记录 |
| 冲突时 | 按任务书做，并回头改规则文件 | — |

WorkBuddy 会读的位置（来源：WorkBuddy 程序本体，未逐项实测，以下是建议用法）：

| 位置 | 建议 |
|---|---|
| 项目根 `CODEBUDDY.md` | 推荐放这里，一个文件写全 |
| `.codebuddy/CODEBUDDY.md` | 不想在项目根多一个文件时用；不要和项目根那份同时写同一条规矩 |
| 项目根 `AGENTS.md` | 团队已在用别的 Coding Agent、已有这份文件时沿用 |
| `.codebuddy/rules/` 下标为始终生效的规则 | 规矩多到要分文件时再用 |

模板如下。尖括号里的按你的项目填，其余照抄；单元一至三把检查命令换成对应单元的那一条（基准各章附录 B.3）。

```markdown
# 项目规则（每轮都要守）

## 项目一句话
杭州民宿经营数据的只读分析服务；本单元产物：<一句话，例如“对话里一句话出区级对比卡的只读插件”>。数据全部是模拟数据。

## 目录约定
- 本文件所在目录就是项目根，也是 git 仓库根；只 commit 这里面的文件。
- app/ 后端；wb-plugin/ WorkBuddy 插件（单元四）；data/ 业务库与运营库；sprint-runs/<时间戳>/ 每一轮的看板、规格、验收记录。
- 课程材料在 <课程根>\v2\，只读。

## 数据只读
- 业务库 data\homestay.db 只读：只用只读连接查，不建表、不改数据、不覆盖文件。
- 开工前存基线（业务库指纹 + 运营库行数），G2 前比对；指纹必须不变。
- 插件只经 HTTP 调后端白名单里的只读接口，不打开库文件，不重算口径。

## 端口
- 后端默认 8801；被占用就换空闲端口并告诉用户。
- 换端口要同步改四处：wb-plugin\.mcp.json 的 HOMESTAY_BASE_URL、重跑 make_snippet.py、~\.workbuddy\mcp.json 的 homestay 条目、检查命令的 --base。

## 检查命令
- 在 <课程根> 执行，同一条跑两次（正向、坏夹具），两次都带 --record：
  python v2\lab\tools\u4_check.py --db <项目目录名>\data\homestay.db --ops <项目目录名>\data\ops.db --base http://127.0.0.1:<端口> --before mine\u4_开工前.txt --card <卡片 JSON> --record <运行目录>\evidence\user-check.md
- 检查脚本一个字不改。

## 禁区
- 不读 v2\checkpoints\（任务书明确允许的那一份除外）；不读 <课程根>\mine\。
- 不改 v2\ 下任何文件。
- 不读、不打印 .env 的值；密钥不进对话、截图、提交。

## 验收口径
- 过没过，只看检查命令的退出码（0 通过，1 不通过）和输出原文；汇报时贴原文，不改写。
- 标“待人眼”的判据留给用户下结论；界面交互没有人亲手点过，不写“已验证”。
- evidence\user-check.md 的人眼三问和结论由用户本人写，任何 agent 不代写。

## 提交纪律
- 用户在 G2 回“放行”之后才 commit；只 commit，不 push。
- 提交前列出暂存区文件清单；.env、data\*.db、.venv\、wb-plugin\out\ 不进提交。
```

## 3 WorkBuddy 差异

对应基准第 2 章（环境）与第 7 章 4.4“G2 之前：装插件，说三句话，命令跑两次，读输出，写三问，亲口放行”、4.5“验收没兑现时，该改哪一栏”、附录 B.1–B.3。

结论：方法、任务书、闸门、检查命令都不变；要换的是装插件、卡片导出、端口配置这三处操作，另有几条宿主限制要知道。

### 3.1 差异总表

| 项 | DSH（基准） | WorkBuddy（本附录） |
|---|---|---|
| 插件目录 | `dsh-plugin\` | `wb-plugin\`：`server.py`、`.mcp.json`、`install\make_snippet.py` 等 |
| 装插件 | 插件页装本地目录，或 `dsh plugin add` | 只走一条路：手改 `~\.workbuddy\mcp.json`（3.2） |
| 卡片谁画 | 宿主按卡片类型渲染，插件只给数据 | 宿主不按卡片类型画卡；数字和排版由插件代码生成，模型只负责原样转贴（3.3） |
| 卡片导出 | 页面控制台 `window.__cardExport()` | 复制插件落盘的 `wb-plugin\out\last_card.json`（3.4） |
| 端口 | `cordis.patch.yml` 的 `config.baseUrl` 一处 | `.mcp.json` 的 `env.HOMESTAY_BASE_URL`，实际生效的是 `~\.workbuddy\mcp.json` 里那份副本（3.5） |
| 规则文件 | 基准未单列 | 项目根 `CODEBUDDY.md`（第 2 节） |
| 技能文档 | 用 DSH 自带的插件开发技能查写法；插件可带技能 | 没有对应的插件开发技能，按 MCP 协议手写；按 3.2 的装法，插件自带的 `skills\` 不加载，模型只看得到工具描述 |
| 错误码 | 基准五个 | 多一个 `E_HOMESTAY_WHITELIST`；地图探索另有两个（3.7） |
| 检查命令 | `u4_check.py` | 同一个脚本，一字不改（3.4） |
| 环境自检 | `env_check.py` 查到 DSH 给绿 | 同一个脚本；“DSH 已安装”一项给黄色，不计入退出码；人工项里写作 coding agent 的那一项，对应你的 WorkBuddy 会话 |

### 3.2 装插件：手改 `~\.workbuddy\mcp.json`

对应基准第 7 章 4.4“二、装插件，说三句话，导出卡片”第 1 步。这一步仍是硬线：你亲手做，不交给任何人代做。

插件页的“安装本地插件”本次交付没有走通，不用它。

第一步，在项目目录生成本机的配置片段。仓库里现成的 `mcp.json.snippet` 写的是生成它那台机器的绝对路径，不能直接贴，必须在你的机器上重新生成：

```powershell
# 在 <项目目录> 执行（示例 unit4-plugin，有 .venv 和 wb-plugin 的那一层）
.venv\Scripts\python wb-plugin\install\make_snippet.py   # 输出“已生成 …\mcp.json.snippet”
Get-Content wb-plugin\install\mcp.json.snippet -Encoding UTF8   # 看一眼：command 指向本机 .venv 的 python.exe，args 指向本机 wb-plugin\server.py
```

第二步，把片段并进 `~\.workbuddy\mcp.json`：

```powershell
# 任意目录执行
notepad "$env:USERPROFILE\.workbuddy\mcp.json"   # 文件不存在时记事本会问是否新建，选“是”，先写入 {}
```

粘贴规则：

| 情况 | 怎么粘 |
|---|---|
| 文件是空的或只有 `{}` | 写成 `{"mcpServers": {"homestay": …}}`，`homestay` 那一项从片段里整项复制 |
| 已有 `mcpServers`，里面有别的条目 | 只把 `homestay` 那一项加进去，原有条目不动 |
| 片段第一行的 `_comment` | 不粘 |

第三步，保存后确认 JSON 没写坏，并看一眼生效的地址：

```powershell
# 任意目录执行；报错说明 JSON 写坏了（多了逗号、少了括号），回记事本改
(Get-Content "$env:USERPROFILE\.workbuddy\mcp.json" -Raw -Encoding UTF8 | ConvertFrom-Json).mcpServers.homestay.env.HOMESTAY_BASE_URL   # 应输出 http://127.0.0.1:8801，或你换后的端口
```

第四步，回 WorkBuddy 新开一个会话（旧会话不刷新工具清单），首次用到这个插件时点“信任”。

第一道自检：在新会话的工具清单里能看到 `homestay_compare`。宿主侧装载在交付环境里没有形成正式验收记录，所以这一条要你亲眼看到才算过；看不到就回 3.8 的排查表，不往下走。

之后的“说三句话”照基准做；模型没有调工具时，补一句“请用 homestay_compare 工具查并原样展示卡片”。

### 3.3 卡片：数字由插件代码生成，模型只转贴

对应基准第 7 章 4.4 二第 2 步与五“读输出，写三问和结论”。

| 你会看到 | 说明 |
|---|---|
| 工具返回里先是一张 Markdown 表格，再是一段 HTML 卡片 | 两样都由插件代码从同一份数据生成；WorkBuddy 不会按卡片类型替你画卡 |
| 模型把表格或卡片贴进回复 | 模型只负责原样转贴，不该改数、不该重画 |
| 显示成一堆 HTML 源码 | 宿主不渲染 HTML，看前面的 Markdown 表格即可 |

模型如果改了数字或自己重画了图，检查命令发现不了：检查命令读的是插件落盘的导出文件，不读对话。这只能靠人眼三问第 1 问。建议做法：在对话里的卡片上抽两三行，与 `mine\card.json` 里同一区的 `label` 逐字对照；对不上，说明模型改写了画面，记进三问，按基准第 7 章 4.5 处理。

### 3.4 卡片导出与检查命令

对应基准第 7 章 4.4 二第 3 步、三“把检查交给 qa”，附录 B.3。

`window.__cardExport()` 在 WorkBuddy 上不可用。插件每次成功出卡，会把这张卡的数据写进 `<项目目录>\wb-plugin\out\last_card.json`，形状与《交付约定_单元四》第 3 节一致。这个文件只在成功出卡后才存在；错误卡不覆盖它。

第三句话出卡之后、停后端之前，复制并核对：

```powershell
# 在 <课程根> 执行
Copy-Item unit4-plugin\wb-plugin\out\last_card.json mine\card.json
(Get-Content mine\card.json -Raw -Encoding UTF8 | ConvertFrom-Json).params   # 看 start、end、metric 三项
```

`params` 的 `start`、`end`、`metric` 必须等于你刚说的那一句。按基准的演示脚本，第三句是“再换成平均房价”，应为 `2025-04-01`、`2025-06-30`、`adr`。对不上，说明拿到的是上一张卡（比如第三句其实出的是错误卡，文件没被覆盖）；这时检查命令照样会判绿，因为它按卡片里自己记的参数去对数。回去重说一句、出卡后重新复制。

检查命令的读法：

| 项 | 说明 |
|---|---|
| 脚本 | `v2\lab\tools\u4_check.py`，不改；参数与基准第 7 章附录 B.3 相同 |
| `--card` | 读的是纯 JSON：正向给 `mine\card.json`，坏夹具给 `v2\lab\fixtures\u4\bad_card.json` |
| 脚本自带提示里的“DSH 控制台”“`window.__cardExport()`”字样 | 忽略，取卡片按本节做 |
| 判定范围 | 只覆盖区级对比卡（`homestay_compare`）和走势卡（`homestay_trend`）；地图卡不在判定范围 |
| `--record` | G2 的两次都建议带上，命令自己把命令行、输出、退出码写进 `user-check.md` 第 1 节 |

基准第 7 章 4.4 三里交给 lead 的那段话照用；话里“回 DSH 新会话”换成“回 WorkBuddy 新会话”。

### 3.5 端口

对应基准第 2 章“栏 8 端口与环境事实怎么写”、第 7 章附录 B.2“起服务和查端口”、《交付约定_单元四》第 2 节。

端口写在 `<项目目录>\wb-plugin\.mcp.json` 的 `env.HOMESTAY_BASE_URL`；但按 3.2 装的插件，实际生效的是 `~\.workbuddy\mcp.json` 里那份副本。换端口按顺序做：

| 步 | 做什么 | 在哪 |
|---|---|---|
| 1 | 改 `wb-plugin\.mcp.json` 的 `HOMESTAY_BASE_URL` | `<项目目录>` |
| 2 | 重跑 `.venv\Scripts\python wb-plugin\install\make_snippet.py` | `<项目目录>` |
| 3 | 用新片段的 `homestay` 一项覆盖 `~\.workbuddy\mcp.json` 里的 `homestay` 条目，再跑一次 3.2 第三步那行核对地址 | 任意目录 |
| 4 | 新开会话 | WorkBuddy |
| 5 | 检查命令的 `--base` 同步换 | `<课程根>` |

插件代码在环境变量缺失时会退回 `http://127.0.0.1:8801`。所以换端口后，要核对错误信息里的地址：`E_HOMESTAY_DOWN` 的原文写着“后端连不上（<地址>）”，地址仍是 8801 而你已换了端口，说明副本没改到，回第 3 步。

| 存成功的样子 | “基线已存”一行，下面业务库、运营库各一行 |

### 3.7 错误码与白名单

对应基准第 7 章 4.4 四“停掉后端，说一句”与《交付约定_单元四》第 1、4 节。

基础任务只用 `GET /api/districts` 一个接口。错误码在基准之外多了下面几个：

| 错误码 | 什么时候出现 | 怎么办 |
|---|---|---|
| `E_HOMESTAY_WHITELIST` | 插件内部白名单拒绝：插件代码要发的请求不在允许列表里 | 属于插件代码的问题，按基准第 7 章 4.5“工具请求里出现白名单外的接口”一行，退回施工 |
| `E_HOMESTAY_NOKEY` | 只在地图探索任务里：要高德底图但没配 key | 自动退回矢量图；见第 5 节 |
| `E_HOMESTAY_MAPIMG` | 只在地图探索任务里：高德静态图出图失败 | 自动退回矢量图；见第 5 节 |

地图探索任务会访问外部的高德静态图接口；基础任务不访问任何外部地址。

### 3.8 宿主限制

| 你会看到什么 | 怎么办 |
|---|---|
| 对话里的内嵌控件白屏，外部脚本（如高德 JS 地图）加载失败 | 内嵌控件只允许从 cdnjs、esm.sh、jsdelivr、unpkg 四个 CDN 加载脚本；其它外部脚本放到右侧页面里用 |

## 4 增量实验：容器化（选做）

对应基准第 6 章 单元三：接在单元三 G2 放行之后做；用到的检查命令与第 6 章附录 B.3 相同。

结论：把单元三的产物装进容器，一条命令起服务；要改对三处，自检时把检查脚本挂进容器，不复制进镜像。

### 4.1 目标与前置条件

| 项 | 内容 |
|---|---|
| 目标 | `docker compose up -d --build` 一条命令起单元三的服务，浏览器能打开，检查命令三行 PASS |
| 前置 | 单元三已 G2 放行并 commit；Docker Desktop 能启动；基础镜像能拉到（4.5） |
| 不做 | 推镜像仓库、上云、改产品功能 |

### 4.2 一条命令起服务

```powershell
# 在 <项目目录> 执行（单元三的项目目录，含 Dockerfile 与 docker-compose.yml）
docker compose up -d --build
docker compose ps   # 状态里有 healthy 即起来了
# 停止：docker compose down（数据在宿主机的 data\ 里，删容器不丢）
```

下面是实测用过的 `docker-compose.yml` 骨架，尖括号按你的项目填：

```yaml
services:
  app:
    build: .
    image: <镜像名>
    container_name: <容器名>
    ports:
      - "<端口>:<端口>"
    env_file:
      - .env                     # 模型地址、模型名、密钥只从 .env 读，不进镜像层
    environment:
      BIND_HOST: 0.0.0.0
      LLM_BASE_URL: http://host.docker.internal:<模型服务端口>/v1
    extra_hosts:
      - "host.docker.internal:host-gateway"
    volumes:
      - ./data:/app/data         # 业务库、运营库留在宿主机
    restart: unless-stopped
```

### 4.3 三个必须改对的地方

改错的表现是起不来，或者页面打不开、白屏。

| 处 | 问题 | 改法 |
|---|---|---|
| 绑定地址可配 | 服务原来固定监听 `127.0.0.1`，容器外访问不到 | 改成从环境变量读，缺省仍是 `127.0.0.1`（本地裸跑行为不变）；容器里设 `BIND_HOST=0.0.0.0` |
| 业务库走挂载 | 业务库被 `.gitignore` 排除、体积大，也不该在镜像里留副本 | 用卷挂载 `./data:/app/data`，宿主机上那份仍是唯一的库；Dockerfile 只 COPY 运行要用的目录，不 COPY 整个项目根，免得 `.env`、库文件进镜像层 |
| 模型地址 | `.env` 里模型地址写的是 `127.0.0.1`，在容器里指的是容器自己 | 在 compose 里覆盖成 `host.docker.internal`，并加 `extra_hosts: host.docker.internal:host-gateway`；模型服务不在本机（填的是外网地址）时不用改 |

项目若是纯标准库实现，镜像不需要装第三方依赖；有 `requirements.txt` 的项目，Dockerfile 里加一步装依赖，构建时要能访问 pip 源。

### 4.4 自检：把检查脚本挂进容器

检查脚本在 `v2\lab\tools\`，课程规定它不进产品代码，所以挂载进容器跑，不 COPY 进镜像。

```powershell
# 在 <课程根> 执行；容器要已经在跑。<容器名>、<镜像名>、<端口> 与 docker-compose.yml 一致
docker run --rm --network container:<容器名> `
  -v "${PWD}\v2\lab\tools:/checker:ro" `
  -v "${PWD}\unit3-agent\data:/app/data" `
  -v "${PWD}\mine:/mine:ro" `
  <镜像名> `
  python /checker/u3_check.py --db data/homestay.db --ops data/ops.db --base http://127.0.0.1:<端口> --before /mine/u3_开工前.txt
# 期望：三行 [PASS]，末行“结论：三件事全部通过 -> 退出码 0”
```

路径改写的坑，已核实：

| 终端 | 要不要 `MSYS_NO_PATHCONV=1` | 原因 |
|---|---|---|
| PowerShell | 不需要 | PowerShell 把 `/checker/u3_check.py` 原样传给 docker |
| Git Bash | 需要，命令前先 `export MSYS_NO_PATHCONV=1` | Git Bash 会把以 `/` 开头的参数改写成 Windows 路径，`/checker/u3_check.py` 会被改写成 Git 安装目录下的 `…/Git/checker/u3_check.py`，容器里找不到脚本 |

### 4.5 镜像拉取

课前检查：

| 项 | 怎么看 |
|---|---|
| Docker Desktop 能启动 | `docker version` 的输出里有 Server 一段 |
| WSL2 已启用 | `wsl --status` 显示默认版本为 2 |
| CPU 虚拟化已开启 | 任务管理器 → 性能 → CPU，“虚拟化”一栏为“已启用”；未启用要进 BIOS 打开 |

镜像源按顺序试，前一个拉不动再换下一个：

| 顺序 | 地址 |
|---|---|
| 首选 | 南京大学 `https://docker.nju.edu.cn/`（官方说明 https://nju-mirror-help.njuer.org/dockerhub.html） |
| 备用 | `https://docker.1ms.run` |
| 备用 | `https://docker.m.daocloud.io` |

```powershell

```

### 4.6 已知限制

| 限制 | 说明 |
|---|---|
| 检查脚本不在镜像里 | 按 4.4 挂载着跑；不要为了方便 COPY 进镜像 |
| 非 root 运行 | 容器以普通用户运行；Windows 下挂载目录的权限由 Docker Desktop 处理，Linux 宿主要保证 `data\` 对容器用户可写 |
| 挂载的库是同一份 | 容器写运营库，写的就是宿主机上的 `ops.db`；抽验期间不要同时在容器和本地各起一份服务 |
| `host.docker.internal` | Docker Desktop 自带；Linux 引擎要靠 `extra_hosts` 那一行 |
