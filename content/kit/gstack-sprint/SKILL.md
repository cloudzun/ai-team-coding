# gstack-sprint：按形态选环的团队交付

> **课程副本**：本文件是课程发放的 gstack-sprint 副本，以原技能为底本，文末附"课程副本说明"。**本课默认用第 1.5 节"L1 课程版"**；第 2–4 节的 9 环与 A/B/C 三形态原文保留，作"完整版（L2）参考"。两者冲突时，按第 1.5 节。发放给学员的副本 name 为 gstack-sprint。

用户只在一头一尾强介入，中间按"介入梯度"异步放权。全过程留痕，看板随时可读。

## 0. 铁律

1. **停手是 lead 对自己的。** 每环结束：审记录 → 判门禁 → 更新 `BOARD.md` → 写 `RING-*.md` → 才进下一环。**先更新看板，再开口汇报。**
2. **子 agent 一律注入 `GSTACK_SESSION_KIND=spawned`**。绝不 `headless`（会 `BLOCKED`）。
3. **gstack 命令走 `gstack_bash` 工具**，`workdir` 设项目根。禁用 PATH 上的 `bash`（是 WSL）。
4. **lead 不写产品代码。** 写代码只由 builder 做，门禁独立性靠这条守住。
5. **一次只开一环。** 上一环门禁没过，不许提前派下一环的 agent。
6. **不确定性不许藏。** 任何"我不确定这是不是他要的"，一律进看板的"⏸ 等你"或"⚡ 可否决"，不许默默按自己的想法走。
7. **判据写意图，不写实现细节。** 写"内容区必须水平铺满视口"，不要写"`documentElement.scrollWidth === innerWidth`"——后者遇到滚动条必然永假，逼得实现去迁就判据。判据一旦写成某个等式，就会有人为了满足等式改实现，而不是改对地方。
8. **同一个概念只能有一个真相源。** 舍入入口、百分比算法、格式化出口、门禁判据，每类只能有一处。出现第二处，两边迟早打架（本项目三次撞同一模式：两个舍入入口 → 11 格显示错；两套饼图百分比 → 同图 3.4% vs 3.3%；两个格式化出口 → 页面 ≠ CLI）。
9. **取证归子 agent，lead 只做记账与判决。** 允许 lead 做：取文件哈希、贴子 agent 交的门禁输出、数证据文件、判 PASS/FAIL 与回退。禁止 lead 做：跑对账、量尺寸、写突变测试、开浏览器验证——一次都不行，做了就会同时犯三个错：污染环境、写错判据、烧自己上下文。

## 1. 第 0 环：R0 分诊（必须先做）

> L1 课程版下，R0 分诊并入环 0（档位与版本计划），按第 1.5 节；存档点上加功能时形态写"B 升级（存档点，不跑 R1/R2）"。

按顺序问，问到即停：

1. **有用户/数据在跑吗？** 没有 → **A 绿地**
2. **改完外部行为必须一模一样吗？** 是 → **C 重构**
3. 否则 → **B 升级**

灰色地带（"加功能顺手重构"）：**拆两轮，先 B 后 C**。混着做既证明不了行为等价，也说不清新功能何时完成。

把判定结果和理由写进 `PLAN.md` 与 `BOARD.md` 头部（形态会决定后面挂哪些环、门禁用什么判据）。

改完形态判定后，再跑**前置检查**：

- [ ] 项目是 git 仓库且有 base 分支（没有先 `git init` + 首个 commit + 建 `main`）
- [ ] `git status` 干净，或有明确说明的 WIP
- [ ] `gstack_bash` 可用（跑 `gstack-doctor` 不 fail）
- [ ] 建运行目录 `<项目根>/sprint-runs/<YYYYMMDD-HHMM>/`，含 `PLAN.md`、`board.json`（初始状态）、`DECISIONS.md`、`evidence/`、`tmp/`。**告诉所有 agent：这个目录只有 lead 能写。**
- [ ] **绿地项目必须自己造门**（A 形态专属）。老项目有现成测试可跑，绿地没有——如果在环 1 不定死"自证环到底跑什么命令"，环 5 会空转。做法：在 `SPEC.md` 里先写清自证脚本要检查哪些不变量，环 4 把它当交付物一起做出来。门禁命令必须**可执行、可判真假、退出码非 0 即红**。

## 1.5 L1 课程版（本课默认形态）

> **本节是课程新增**，不在原技能里。它把两份来源合成一个可直接执行的流程：1) **L1 演示档的纪律骨架**（档位、3 个独立判断、只 commit、两通道验收）；2) **试跑长出来的团队形态**（看板、每环 `RING-N.md`、G1/G2、收尾）。来源标注写法：〔画像 §n〕= L1 演示档画像（课程设计阶段的档位文件）第 n 节；〔试跑记录〕= 试跑的看板与环记录；〔快照 §n〕= 本文件对应小节；〔本课安排〕= 没有试跑证据、为课堂做的规定，讲师可按本班实测的耗时折算时间盒。
> 其余各节里与本节冲突的地方，都按本节。
>
> **试跑偏差声明**：本节要求环 1 `office-hours`、环 2 `spec`、环 3 的规格评审角色（`plan-ceo-review`、`plan-eng-review`，有界面加 `plan-design-review`，有开发者接口加 `plan-devex-review`，见 1.5.2）、环 5 `qa-only` 都**必跑**，且是作为技能加载运行。试跑里，这些技能只有 `plan-eng-review` 被加载过（前两轮的评审子 agent），`office-hours`、`spec`、`qa-only` 以及 `plan-ceo-review`、`plan-design-review`、`plan-devex-review` 一次都没有作为技能加载（涉 UI 的那轮也没派设计评审），各环是 lead 按环表和任务书派子 agent 完成的。这是试跑相对本节的**偏差**，不是规则；课上在对照试跑里要如实讲，不要把试跑的做法当成"可以不跑"的依据。

### 1.5.1 什么时候用

- **用**：演示 / MVP 级交付——给人看、给人试的版本。两种起点：**绿地**（从空目录起，本课单元一）和**在存档点上加功能**（本课单元二至四，存档点即上一轮已 commit 的版本）〔画像 §0；试跑两轮均为后者〕。
- **不用**：要上线、要给客户长期用、要负维护责任的交付——走第 2–4 节完整版（L2）。
- **形态申报**：绿地写"A 绿地"；存档点上加功能写"B 升级（存档点，不跑 R1/R2）"。试跑两轮的看板写"B 升级"，但 B 形态的考古（R1）、基线（R2）、迁移（T1）都没跑，教学上要如实说明；本课用**回归判据**承担 R2 的职能（见 1.5.2 环 2）〔试跑记录的判据含 R 类回归 4 条；快照 §3 R2 门禁"关键路径 ≥3 条有可复现证据"〕。
- **预算**：返工 ≤1 个缺陷（按缺陷算，不按修改轮次）、提交 ≤3 次、判据 ≤25 条〔画像 §0〕。画像原值"4–5 小时"是真实演示档的预算，课堂装不下，**时间盒由讲师按课时折算，写进环 0 的版本计划**〔本课安排〕。只排粗粒度的先后：先环 0–2（计划、立项、规格），再环 3 评审，再环 4 施工，最后环 5–7（验收、放行、收尾）；课堂单元另含讲解与对照两段，见教材第 4 章。环 3 按学时收尾，默认按"精简方式"（不写技能自带的完整报告、不跑技能内的 Spec Review Loop、不出视觉 mockup）跑三个以上评审角色加 Outside Voice；时间紧就调时间盒，不砍角色。要求完整方式跑的单元，要单独标明并另测时间，不适用精简方式的用时。

**为什么 8 环**：L1 画像是 0–6 共 7 行、称"六步"〔画像 §1〕；试跑把它套进看板后长成 8 环（多一个收尾环，G2 单列）〔试跑 `board.json` rings 8 条〕；后一轮又多出 `2b`（测试实例）和独立的 `G1` 环，前者只适用于插件类交付，后者本课并进环 0 与环 3，不另立环〔试跑 `board.json`〕。

**各环要点**

- **环 0**：**开场先告诉学员当前工作目录**（学员在课程工作区、即含 `v2` 的那一层新开会话即可，不要求自己敲建目录命令）〔本课安排，2026-11 实测〕。然后 lead 做三件事——一是按第 1 节三问判形态；二是写版本计划草案（本轮要证明的一件事、不做清单、时间盒与预算、判据条数上限、超预算时的砍项顺序、子 agent 编制与各自写域）；三是在 DSH 任务板建 8 条任务（环 0–7），每环一条、`blocked_by` 串成链、带 `write_scopes`〔试跑建 8 条 team_task；快照 §6 层 2〕。写完去**问用户 G1**（1.5.5）。**G1 未回，不派任何 builder**〔本课安排；试跑里有"G1 未回按推荐开工"，被记为问题〕。**环 0 只问 G1（档位与版本计划）；口径歧义的 A/B 不在环 0 问，留到环 2 由 `planner` 探数后再问**〔本课安排，2026-11 实测〕。
  **开工前准备**：任务书栏 8 授权后，由 lead 做，并把命令和输出贴给学员看——建项目目录 `unitN-xxx` 和 `mine`（单元二起，从上一单元已 commit 的版本复制，含 `.env`）、`git init` 或保留历史、把业务库开工前指纹存进 `mine\`，然后把工作目录切到项目目录再开工。开工前还要确认项目目录的 `.gitignore` 里有 `.env`，没有就加上。学员只看输出：项目目录在、指纹文件在、`.gitignore` 有 `.env`。**`mine\` 里只放这一份指纹，之后 lead 与子 agent 都不读不改**〔本课安排，2026-11 实测〕。
- **环 1 立项**：**必跑 `office-hours`，由 lead 在主会话加载运行**。原因：它全程向人提问，在子 agent 里以 spawned 运行会自动选推荐项、问不到人；它的第二意见（Phase 3.5）也要再派 agent，子 agent 派不了。提问由 lead **带推荐自答**；属于 1.5.8 所列重大问题的（如备选方案怎么选、前提成不成立、范围增减），列 A/B 交用户拍，不自己定。**按 L1 裁剪只跑 Phase 1（上下文收集）、Phase 3（前提挑战）、Phase 4（备选方案）、Phase 5（设计文档）**；Phase 2 诊断/头脑风暴、第二意见、视觉探索、资源推荐都不跑〔画像 §2〕。**跳过 Phase 2 后的衔接**：设计文档里本应由 Phase 2 填的字段（问题陈述、约束、成功标准等），直接从任务书和 Phase 1 收集的上下文里抽取，不另补一轮诊断；**Phase 5 末尾自带的 Spec Review Loop 本课不跑**（规格评审由环 3 的评审角色承担，不在环 1 重复派 reviewer）。产出**设计文档**，lead 把路径记入 `RING-1.md` 并复制一份进运行目录；再据此写 `L1-BRIEF.md`——由 lead 派 `planner` 整理（`planner` 只转写设计文档里已定的内容，不增删前提，不确定处交回 lead；lead 自己不写，见 1.5.3）。`L1-BRIEF.md` 六节固定——一句话要证明的事 / 谁看、看完做什么决定 / 演示脚本 3–5 步 / 前提与怎么证伪 / 不做与"可造假"清单 / 档位与预算〔画像 §2〕。门禁：第 1 节一句话可判真假；演示脚本至少 3 步；每条前提有证伪动作，没有的标"未证"；"可造假"逐条写了 UI 上怎么标"模拟数据"。
- **环 2 规格**：**必跑 `spec`，L1 参数 `--no-gate --no-dedupe --no-execute --plan-file <路径>`**（`<路径>` 指向运行目录里的 `L1-SPEC.md`；`--no-execute` 只落规格文件、不让 `spec` 的 Phase 5 自动起 agent 去实施，别名 `--file-only`，实施要等环 3 评审和 G1 之后由 `builder` 做），**不建 issue**。`planner` 子 agent 以 spawned 运行它：技能的提问自动选推荐项，`planner` 把不确定的点写进回报的"我不确定的"，由 lead 判断是自己定还是升级（1.5.8）〔画像 §3〕。**规格里必须有一节"交付契约"，单元一由 lead 把渔具包《导出契约》全文交给 `planner`，原样写入，不许 `planner` 自拟形状；其他单元由 `planner` 在这一节写明交付物形状（见 1.5.10）；两种情况都不作为待裁定项列 A/B 问人。** 每条验收标准可机器判；规格不复述立项第 1 节以外的目标〔画像 §3〕。**规格里每一条"必须/用/应"都要有对应判据，否则只是建议**〔画像 §13.3〕。存档点上加功能时，判据里要有"回归"一类（至少 3 条老功能关键路径），并列出需要**人眼**才能判的几条（观感、图片内容），标为人眼判据〔试跑的 D/L/R/H 四类判据〕。**口径歧义的 A/B 在这一环问**：`planner` 探数后，把需要人定的口径写进回报的"我不确定的"，lead 在回复正文里列 A/B 交学员（1.5.8）〔本课安排，2026-11 实测〕。
- **环 3 规格评审**：**必跑**，按 `autoplan` 选角色的规则选评审角色〔`autoplan/SKILL.md` 第 712–715 行：CEO、Design（仅有界面）、DevEx（仅有开发者接口）、Eng 四路〕：**`plan-ceo-review`、`plan-eng-review` 每轮必跑；有界面时加 `plan-design-review`（单元一至四都有界面，单元四是卡片界面）；有开发者接口时加 `plan-devex-review`（单元四的插件工具接口）；每单元至少 3 个角色**。**不跑 `autoplan` 本体**：它要派 agent，子 agent 不能再派 agent，L1 课程版由 lead 在主会话**依次**跑各角色代替〔画像 §4；快照第 205 行"agent 不能再派子 agent"〕。各评审技能的提问也靠人答，在子 agent 里只会自动选推荐项，所以 lead 在主会话里答（带推荐；重大问题按 1.5.8 列 A/B 交用户）。**Outside Voice 按条件跑**（这四个评审技能各自都带 Outside Voice，走 `codex exec` 或派 agent，评审主体本身不依赖 codex）：本机有 codex，或宿主能派**换了模型家族**的子 agent，就跑——lead 把技能构造好的挑战提示派给一个换了模型家族的子 agent（名 `outside-voice`，只读）承担，意见原样收进 `L1-REVIEW.md`、再按技能的决策流程逐条处置〔快照 §7"reviewer 必须换 provider"〕。**两样都没有属于降级：跳过 Outside Voice 这一步（评审主体照跑），在看板 `auto[]` 记一条，写明代价——同一个模型审自己写的规格，"第二意见"不成立；用户可否决**〔试跑里评审与作者同模型被记为缺陷〕。每条发现要写成"照它实现会打红哪几条判据"，写不出这句的不算发现；CRITICAL/HIGH 全部关闭或有书面接受理由；结论落回 `L1-SPEC.md` 修订，不能只留在对话里。**评审必须核对"规格与交付契约一致"**：lead 在评审时逐项对照本单元的交付契约（单元一是渔具包《导出契约》：字段名 `points`、比例类 0–1 小数、`label` 取页面显示文字、对象 id 与系列名清单；其他单元对照规格"交付契约"一节写明的形状与检查命令的输入，见 1.5.10），不一致一律按 CRITICAL 记，写成"照它实现，本单元的检查命令会判红"，并回写 SPEC，不留到施工后。**每个评审角色加载后，都要先执行它自己正文开头的前置段**（`gstack-skill-start`，见 1.5.4），不能只在第一个角色上执行。**检查命令与坏夹具只禁 `builder` 读，评审角色（含 `outside-voice`）可以读，用来核对边界**（1.5.3）〔本课安排，2026-11 实测〕。**环 3 按时间盒收尾，盒子长短由讲师按课时定**；超时就调时间盒，角色照跑，不改成"可选"〔本课安排〕。

**精简方式与完整方式**：L1 默认按精简方式跑评审技能——不写技能自带的 GSTACK REVIEW REPORT 与计划文件、不跑技能内部的 Spec Review Loop、不出视觉 mockup，在 `L1-REVIEW.md` 开头写明"精简方式"。某单元要求完整方式时，要单独标注并另测时间，不得套用精简方式的用时。
- **环 4 施工**：**没有对应技能**，由 `builder` 子 agent 写代码。只写自己的 `write_scopes`；**只跑既有判据，不新增判据**；不顺手重构、不扩需求，新冒出的需求记 `TODOS.md`〔画像 §5〕。builder 看不到验收者的材料，验收者也不许看 builder 的自测记录；`v2\checkpoints\`、检查命令、坏夹具，builder 一律不读（1.5.3）。
- **环 5 独立验收（含自证）**：**必跑 `qa-only`**（只报告、不改代码、不改产品测试），由 `qa`（或 `verifier`）子 agent 以 spawned 运行；它不派 agent，不靠人答问，适合放在子 agent 里。验收者从 `L1-SPEC.md` 自己读判据，**自己算期望值**，逐条打；不改代码，不看 builder 自测记录〔画像 §6〕。"自证"在本课的含义：**对关键机器判据各做一次坏输入对照**，证明它会红，不是桩——造法见第 14 节；对照用的夹具放 `tmp/`，不进交付物，不算新增判据。**L1 课程版只对关键机器判据做坏输入对照即可，不要求对全部判据（最多 25 条）逐一造突变**，免得课堂超时〔本课安排；快照 §14；试跑 `RING-5`：复验者用正向对照证明扫描有效〕。验收失败按第 10 节回退。**第二通道（学员抽验）要有产物**：`qa` 交报告后，本单元的检查命令可以交 `qa` 跑——同一条命令两次（正向一次、负向一次），命令与输出用 `--record` 自动写进 `evidence/user-check.md`；学员自己读输出，在同一份文件里写人眼三问各一行加结论一行，**这四行 lead 与 `qa` 不得代写**（格式与放行条件见 1.5.11）。单元三另要求学员亲手在页面上巡检、提交两条建议、批准一条，lead 与 `qa` 不得代点；单元四另要求学员亲手装插件、在对话里说三句话出卡、导出卡片，lead 与 `qa` 不得代做（两条都是硬线，见 1.5.11）〔本课安排，2026-11 实测〕。供抽验的产品服务由 `qa` 子 agent 或用户自己起，lead 不起。
- **环 6 G2 放行与 commit**：G2 之后 **lead 手工 commit，禁用 `ship`**（它无条件 merge 主干并 push）。**lead 在向用户提 G2 之前，先检查 1.5.11 的放行条件（抽验记录存在且含学员自己写的人眼三问各一行与结论一行、所有"待人眼"判据已关闭；单元三另核学员亲手的页面操作已做，单元四另核学员亲手装插件、说三句话出卡、导出卡片已做），不满足就不问 G2，先告诉用户缺什么。**满足后 lead 把**证据包**摆给用户——演示脚本每一步的证据、`L1-QA.md`、未解决缺陷与"没做到的"、暂存区文件清单与敏感串扫描结果、`evidence/user-check.md`；用户放行后 lead 才 commit〔画像 §7；试跑记录〕。commit 按清单逐项 `git add`，不用 `git add -A`；提交信息末尾带 `[L1]`〔画像 §7；试跑逐个 add〕。提问 G2 时写明"放行同时覆盖环 7 收尾文档的追加 commit"，用户回放行即覆盖，收尾不再单独问一次。lead 摆证据时只贴 `qa` 子 agent 交的结论原文与文件清单，不自己起服务、不读截图、不据截图下观感结论（见 1.5.3）。
- **环 7 收尾**：**不跑 `retro`**，由 `closer` 写 `HANDOFF.md` 与"不要再犯"清单；`retro` 作完整版（L2）参考，放模块八。`HANDOFF.md`（做了什么 / 怎么跑 / 已知限制 / 欠债 / 不要再犯）、`TODOS.md`、把本轮人拍板的决定写成 `precedents`、看板置完成〔快照 §11、§16〕。收尾文档的追加 commit 已随 G2 获准（环 6 提问时写明），lead 照清单逐项 `git add` 提交，不再单独问人；仍只 commit、不 push。**收尾时 lead 列出自己起过的服务与端口（若有）并逐一关掉，复查端口已释放；`qa` 或学员起的服务，由起的人停，lead 只核对端口无监听**〔本课安排，2026-11 实测〕。多轮迭代时先把上一轮文档复制为 `*.r{n-1}.md` 再重写同名文件，不用 v2/v3 命名〔画像 §9〕。

### 1.5.3 编制：lead 与子 agent

| 角色 | agent 名 | 环 | 做什么 | 权限 |
|---|---|---|---|---|
| lead | `lead` | 全程 | 编排、判门禁、更看板、写 RING、向用户提问；**在主会话加载运行 `office-hours`（环 1）与环 3 的各评审角色（`plan-ceo-review`、`plan-eng-review`，按条件加 `plan-design-review`、`plan-devex-review`）**，答它们的提问；**不写产品代码，不亲自取证** | 全权 |
| planner | `planner` | 1–2 | 环 1：据 lead 跑出的设计文档整理 `L1-BRIEF.md`；环 2：以 spawned 运行 `spec` 写 SPEC；遇不确定处交回，不自己猜 | 写 BRIEF/SPEC/参考算法 |
| outside-voice | `outside-voice`（须**换模型家族**；条件见 1.5.2 环 3） | 3 | 承担各评审角色的 Outside Voice：独立挑战规格；它是子 agent，不再派人；没有 codex、也派不出换家族的子 agent 时不设，按降级记 `auto[]` | 只读 |
| builder | `builder-1`（`builder-2`） | 4 | 写代码（无对应技能） | 只写自己的 `write_scopes` |
| qa（或 verifier） | `qa` / `verifier` | 5 | 以 spawned 运行 `qa-only` + 坏输入对照 | 只读；写验收报告与 `tmp/` |
| closer | `closer` | 7 | 写 HANDOFF、TODOS 与"不要再犯"清单（不跑 `retro`） | 写文档 |

- **"3 个独立判断"指 3 个不可替代的判断**：评审（规格能不能判）、施工（怎么实现）、验收（是否达标）——这三件换同一个人做就成了自审自批〔画像 §1.5〕。本课评审由 `lead` 依次跑环 3 的各评审角色、`outside-voice` 换模型家族再挑战一遍承担（后者按条件，降级时没有）；规格是 `planner` 写的，不是 lead 写的，所以 lead 评审不构成自审。`planner` 与 `closer` 是 lead 的"笔头"，不做判断，不计入这三个；每轮各最多 1 个。lead 自己写 BRIEF/SPEC 的做法在试跑里被用户当场纠正，沉淀为判例"lead 只编排与判门禁，探数、写规格草案、评审、施工、验收都派子 agent"〔试跑记录〕；本课对其中"评审"一项只作一处调整：技能内部要再派 agent，子 agent 做不了，所以由 lead 跑，Outside Voice 仍派子 agent。
- **技能跑在哪里的判据**：**技能内部要再派 agent、调 codex，或靠提问才能推进的，由 lead 在主会话跑；其余由子 agent 以 `GSTACK_SESSION_KIND=spawned` 跑。** 依据：快照第 8 节环境事实写明"agent 不能再派子 agent：/autoplan 这类内部要派活的技能会降级"；子 agent 以 spawned 运行时，gstack 技能不再向人提问而是自动选推荐项，**问不到人**〔快照 §0 铁律 2、§10〕。逐个核对本机技能文件：`office-hours`（全程提问；第二意见要再派 agent 或调 codex）、环 3 的 `plan-ceo-review`、`plan-eng-review`、`plan-design-review`、`plan-devex-review`（提问多；四个技能各自都带 Outside Voice，走 codex 或再派 Agent 子代理）→ 都归 lead 主会话；`spec`、`qa-only` 内部不派 agent，spawned 下自动选推荐项即可 → 归子 agent。向用户提问一律由 lead 在主会话里做〔本课安排〕。
- **与铁律 4、铁律 9 不冲突**：铁律 4 禁的是 lead 写**产品代码**，铁律 9 禁的是 lead **取证**（跑对账、量尺寸、写突变测试、开浏览器验证）。lead 跑 `office-hours` 和环 3 各评审角色产出的是**设计文档和评审意见**，既不是产品代码，也不是对产品的取证，不在这两条的禁止范围内。lead 做完这些事，仍只判门禁、不碰代码、不碰验收取证；验收取证照旧归 `qa`/`verifier`。
- **铁律 9 在环 6 的边界**：一是供用户抽验的产品服务，由 `qa` 子 agent（单独派一轮，把地址与停止办法写进回报）或用户自己起，**lead 不自己起服务**，也不替人停服务；起服务的人负责用完停掉、复查端口无监听（1.5.9 #9）。二是**lead 不读 `qa` 的截图、不据截图对产品下观感判断**；需要让用户看图，只给文件路径清单，由用户自己打开；lead 能做的仍是数文件、取哈希、贴 `qa` 的结论原文。三是**lead 不写用户的长期记忆**（宿主提供的"记住这条"类工具）：课程运行会改学员机上的长期记忆，是对学员环境的副作用；确需写（用户明确要求保存），先在看板 `auto[]` 记一条写明要写的内容，用户可否决。四是**单元三的页面操作**：学员亲手在页面上点一次巡检、提交两条建议、批准一条，lead 与 `qa` 都不得代点，即使学员授权也不行；学员休息时授权代办也不包括这一项〔本课安排，2026-11 实测〕。**单元四同理**：学员亲手在 DSH 里装插件、在对话里说三句话出卡、导出卡片，lead 与 `qa` 都不得代做，即使学员授权也不行；学员休息时授权代办也不包括这一项〔本课安排，2026-11-23 用户追加〕。
- **防抄**：`v2\checkpoints\`（课程的参考实现）不给任何子 agent 读，也不复制进项目目录；检查命令与坏夹具只禁 `builder` 读，评审角色（含 `outside-voice`）可以读，用来核对边界，`qa` 照常跑。lead 派发时把这一条写进每个子 agent 的 prompt。单元四例外：项目目录本来就是从阶段三存档点复制来的后端，这一份可以读和改；仍不读 `v2\checkpoints\stage4\`〔本课安排，2026-11 实测〕。
- 同环最多 2 个 builder，`write_scopes` 重叠就串行〔画像 §1，快照 §7 上限 3，课程取 2〕。
- 验收者很久没有产出就换人；lead 不验收。多久算"很久"，由讲师按本班课时和实际用时掌握〔本课安排〕。
- 派发模板见第 8 节，回报格式含"我不确定的"，不得省略。

**子 agent 没有 bash 时**：`spec`、`qa-only` 跑不了前置段与脚本时（技能原文只有前置段协议缺失时的安全默认，没有"没有 bash"的降级写法）：`spec` 无法运行时，由 `planner` 按 `spec` 的五个阶段手写 `L1-SPEC.md`；`qa-only` 无法运行时，由 `qa` 按规格判据逐条手测并写 `L1-QA.md`（附命令输出）；两者都在对应的 `RING-N.md` 与看板里标"降级"，不要写成正常跑通。Windows 上 bash 一律用 `C:\Program Files\Git\bin\bash.exe`，不用 PATH 上的 `bash`（是 WSL）〔本课安排，2026-11 实测〕。

### 1.5.5 G1 与 G2（统一定义）

> 这里的 G1/G2 是**两道人闸门**，与第 2 节阶段组名 G0–G3 同名不同义；第 5 节"G3 不可逆动作"中的 commit，在本课归 G2。

| 闸门 | 含义 | 什么时候问 | 回答方式 | 没回怎么办 |
|---|---|---|---|---|
| **G1** | **开工前**确认**档位和版本计划** | 环 0 一次（环 0 只问这一件）；之后环 1–3 里只要出现"做什么"的变化（范围增减、验收标准变化、前提被证伪、预算或判据条数变化）就再问一次，**回了才派 builder**；技术实现选型不属 G1（见下） | 用户回字母（A/B） | 不开工，不按推荐执行 |
| **G2** | **commit 前**看证据再放行 | 环 5 验收通过、且 1.5.11 的放行条件满足后（检查命令两次已由 `qa` 记录，学员自己写的人眼三问各一行与结论一行在；单元三另有学员亲手的页面操作，单元四另有学员亲手装插件、说三句话出卡、导出卡片），lead 摆证据包（1.5.2 环 6） | 学员亲口回"放行"，或"打回 + 退回哪一环" | 不 commit；缺那四行（或单元三缺页面亲手操作、单元四缺亲手装插件出卡导出）时 lead 不问 G2，先提示学员补 |

**G1 触点收紧**（技术选型不该问人，收尾 commit 并入 G2）：
- G1 只有环 0 那一次，加环 1–3 里出现 1.5.8 的前三类变化时的重问，其余都不是 G1。
- **技术实现选型不属 G1**——编程语言、依赖库、服务形态、静态资源从哪取、端口等"怎么搭"，不改变"做什么"，由 lead 带推荐自定、记看板 `auto[]`（写明理由与重做代价），用户事后可否决，不列 A/B 问人。同类问题不许一次问人、一次自定。
- **交付契约不是 G1 的待裁定项**：形状、字段名、量级单元一由渔具包《导出契约》规定，其他单元由规格环写明（1.5.10），lead 不拿它列 A/B。
- **收尾 commit 并入 G2**：不单独再问一次（见 1.5.2 环 6、环 7）。
- **环 0 只问 G1**：口径歧义的 A/B 留到环 2，由 `planner` 探数后再问；不在环 0 一并问〔本课安排，2026-11 实测〕。
- **G2 的前置条件是学员亲写的四行**：检查命令可交 `qa` 跑，但人眼三问各一行与结论一行必须是学员自己读输出后写的，lead 与 `qa` 不得代写；缺这四行，lead 不问 G2（1.5.11）〔本课安排，2026-11 实测〕。

来源：G1 = 画像"拍档位"〔画像 §1 环 0〕加试跑"版本计划确认"〔试跑看板 `G1` 环〕；G2 = 画像"commit 前人看证据"〔画像 §7 第 4 条〕。两者在试跑里同名不同义（画像的 G1 只拍档位，试跑的 G1 是确认版本计划），本课合并定义；试跑前两轮的 G2 是一次性授权给 lead 自判，**本课不允许**〔画像 §7 要求人确认；试跑 `PLAN.md` 环 6〕。

### 1.5.6 看板与 RING 怎么记

- **看板**：`board.json` 是单一数据源，每环结束改状态，然后跑 `node <渔具包>/tools/gen-board.mjs <项目根>/sprint-runs/<ts>/board.json` 生成 `BOARD.html` + `BOARD.md`，用 `present` 发给用户，**先更新看板，再开口汇报**，汇报用第 6 节三行话术〔快照 §6〕。`<渔具包>` 指讲师随课发放的目录，其中有 `tools/gen-board.mjs` 和样例 `tools/demo/board.json`。`<渔具包>` 的实际路径由用户在任务书或课程包说明中指定；环 0 若找不到 `<渔具包>/tools/gen-board.mjs`，lead 在主会话向用户确认实际路径，不自行猜测。
- **字段用法**：`form` 写 1.5.1 的形态申报；8 个环填进 `rings[]`，返工另列一行（如 `4b`）；用户要回的问题进 `waiting[]`；lead 自决的进 `auto[]`（⚡）；已拍板的进 `decisions[]`，`who` 写"人"或"lead"、`vetoable` 写可否否决；判例进 `precedents[]`〔画像 §14；试跑 `board.json`〕。
- **三条纪律**：`state` 只能由实际结果填，没跑完不许写 `done`；`duration` 一律从时间戳算，**不采信子 agent 自报**（试跑里自报虚高 3–9 倍，lead 凭印象估的用时也会虚高）；决策点必须进 `decisions[]`，不能只留在对话里〔画像 §13.1、§14〕。
- **写 `board.json` 的方式**：只许用 `write` / `edit` 工具改，**禁止**用 PowerShell 的 `ConvertTo-Json | Set-Content`（Windows PowerShell 5.1 会写入 BOM，生成器解析失败）、**也禁止**用字符串或正则对 JSON 整段替换（容易截断，改坏结构）。改完立即跑生成器，没报错才算写好〔本课安排〕。
- **改完立即生成并核对**：每次改 `board.json` 后立即运行看板生成，并核对生成物（`BOARD.md`、`BOARD.html`）的更新时间戳是刚刚的，没报错、时间戳对才算写好。看板摘要（三行话术）与看板链接写在回复正文里，不只靠 `present` 的文件卡片（回合未结束时文件卡片不显示）〔本课安排，2026-11 实测〕。
- **降级如实写**：子 agent 没有 bash、`spec` 或 `qa-only` 按降级手写的，在 `RING-N.md` 与看板的该环 `gate`/`record` 里写"降级"，并记一条 `auto[]`（1.5.4）〔本课安排，2026-11 实测〕。
- **更新时机**：每环结束更新一次〔快照 §0 铁律 1；试跑每环都有记录〕。画像里"只在 3 个检查点更新"是为很短的环节降频，本课不采用〔本课安排：课堂要让用户随时看得见"现在在哪"〕。
- **RING 记录**：每环一份 `RING-<N>.md`，五段（做了什么 / 交付文件 / 命令与输出 / 门禁判定 / 决策与回退），**缺一段门禁算没过**；本课每份几行到二十几行即可〔快照 §9；试跑的 RING 为 12–24 行〕。画像的"只要一份 `L1-DEMO.md`"在本课由 8 份 RING 加看板取代〔试跑的做法〕。
- **DSH 任务板**：每环一个任务，只表达"进行到哪"，不承载决策内容〔快照 §6 层 2〕。

### 1.5.7 用户（学员）每环做什么

### 1.5.8 lead 怎么向用户提问

- **格式**：在正文里用第 5 节固定格式列 **A/B 两个选项，各带代价，给出推荐**，用户**回字母**即可。A/B 选项、看板链接和待决事项**写在回复正文里**，不只放文件卡片（回合未结束时文件卡片不显示）。不用 `ask_user_question`〔试跑期间该工具基本没用，全部是正文列选项、用户回字母〕。第 5 节"未回即执行默认"只用于 ⚡ 级小决策；**G1、G2 没有默认，不回不动**〔本课安排〕。
- **只有重大问题才升级给人（⏸）**：1) 范围增减；2) 验收标准变化；3) 前提被证伪；4) 对外可见行为变化、契约变化、超出版本计划的改动或成本翻倍；5) commit（G2）。其余都是 lead 带推荐项自己定，记入 `auto[]`，用户事后可否决〔快照 §5；试跑的 13 条决定里 lead 自定 8 条、用户拍 5 条〕。**技术实现选型（语言、库、服务形态、资源来源、端口）不在 1)–5) 之内，一律 lead 自定**；交付契约由课程统一规定，不列 A/B（1.5.10）。**合并问多条时**，每条独立编号、各带推荐与代价，并在末尾提醒"回'全推荐'即逐条按推荐，不再逐条把关"；涉及验收口径或对外契约的条目，lead 在提问里单独标出，不得靠"全推荐"带过〔本课安排〕。
- **归口**：环 1–3 里出现的前三类（范围、验收标准、前提的变化）归 **G1 重问**；环 4 施工中若出现第 4 类（对外可见行为、契约等）重大变更，同样按 `⏸` 停下问人，问题进看板 `waiting[]`；变更涉及改规格的，回环 2 并走 G1，回了才继续〔本课安排；对齐 1.5.5 与本节〕。
- **子 agent 里的提问**：`planner`（跑 `spec`）、`qa`/`verifier`（跑 `qa-only`）、`outside-voice` 等遇到技能提问会自动选推荐项，它们把不确定的点写进回报的"我不确定的"，由 lead 判断是自己定还是升级〔快照 §8、§10〕。`office-hours` 和环 3 各评审技能（`plan-ceo-review`、`plan-eng-review`、`plan-design-review`、`plan-devex-review`）的提问则由 lead 在主会话里直接回答：带推荐自答，属于上面 1)–5) 的列 A/B 交用户拍。
- **环 0 与环 2 的分工**：环 0 只问 G1（档位与版本计划）；口径歧义的 A/B 留到环 2，由 `planner` 探数后再问〔本课安排，2026-11 实测〕。

### 1.5.10 交付契约与每单元的检查命令

**为什么单列**：规格若自己定交付形状，例如把图表点位写成 `series[].data`、比例写成百分数 63.7，而课程工具箱的检查命令只认 `points`、比例按 0–1 小数判，数字全对，学员第一次对账也会有图判红。要是把交付形状当成"待裁定项"，用户回"全推荐"就放过了。所以形状不再由规格自定，也不再列 A/B。

**唯一真相源**：单元一的导出契约是渔具包里的《导出契约》（`<渔具包>/导出契约.md`）；其他单元由规格环在 `L1-SPEC.md` 的"交付契约"一节里写明交付物的形状，按渔具包对应的交付约定写（单元二《交付约定_单元二》、单元三《交付约定_单元三》，lead 派发时把该页原文交给 `planner`，不转述），检查命令与坏夹具见该单元章节。`<渔具包>` 的实际路径由用户在任务书或课程包说明中指定，找不到时 lead 向用户确认，不自行猜测。本节只写 lead 怎么用契约；单元一与《导出契约》不一致时，按《导出契约》。

**每单元一条检查命令**：正向必须 PASS；负向必须变红——单元一的负向是把系列对调（`--swap`），其他单元的负向是该单元提供的坏输入夹具；再加库文件指纹前后不变。单元一的检查命令是 `chart_check.py`，其余单元的命令见该单元章节。检查命令可以交 `qa` 跑，一条命令两次（正向一次、负向一次），用 `--record` 把命令与输出自动写进 `evidence/user-check.md`；检查命令与坏夹具只禁 `builder` 读，评审角色可读。**检查命令不依赖模型文字**：产品里大模型超时或不可达而回退文字模板，不算缺陷〔本课安排，2026-11 实测〕。

**契约要点（以单元一《导出契约》为例）**（lead 派发时把《导出契约》原文交给 `planner`，不转述）：
- 页面提供全局函数 `window.__chartExport()`，同步或返回 Promise 均可，返回可转成 JSON 的对象，顶层字段固定为 `page`、`filters`、`kpis`、`charts`。
- 图表的点位固定写成 `charts[].series[].points[]`，每个点是 `{x, value, label}`。字段名只用 `points`，不用 `data`、`values` 等别名。`kpis[]` 每项是 `{id, value, label}`。
- **比例类数值一律用 0–1 小数**（入住率、占比、同比变化率等；百分点差也用 0–1 小数差：0.05 就是 5 个百分点），`value` 不写百分数 63.7；金额、评分等非比例数取原值。`value` 取自已渲染的图表实例或页面节点，不转发后端原始数据。
- **`label` 是页面上实际显示的文字**（如"63.7%"），取不到写 `null`；显示用百分数，导出的 `value` 仍是 0–1 小数，两者并存，不要把显示值塞进 `value`。
- 对象 id 与系列名由规格列清单；工具箱里参考 SQL 的段头 id、系列名与它逐字一致。
- 其他单元：由 `planner` 在规格的"交付契约"一节写明交付物形状，按渔具包对应的交付约定写，评审逐项核对，检查命令按它读输入；该单元那一条检查命令可以交 `qa` 跑，学员读输出即可，不需要学契约细节。

**三道把关**：
1. **环 2**：`planner` 把本单元的契约写进 `L1-SPEC.md` 的"交付契约"一节（单元一原样取自《导出契约》）；形状、字段名、量级不是待裁定项，不进 1.5.8 的问人清单，不接受"按推荐"改写。任务书若写了与契约冲突的形状，lead 按契约办，并向用户说明一句、记看板 `decisions[]`。
2. **环 3**：评审时核对 SPEC 的交付契约一节与本单元契约逐项一致（单元一如 `points`、0–1、`label`、id 与系列名），不一致按 CRITICAL 记并回写（1.5.2 环 3）。
3. **G2 前硬门禁**：本单元的检查命令由 `qa` 跑两次，**正向必须全部 PASS，负向必须变红**（单元一是对调系列 `--swap`，其他单元是坏输入夹具），库文件指纹前后不变，命令与输出由 `--record` 自动写进 `evidence/user-check.md`；学员自己读输出，写人眼三问各一行加结论一行，缺这四行 lead 不问 G2（1.5.11）。正向就红的，先查是不是字段名或量级不合契约，再查口径；正向、负向不都过，不得放行 G2。

### 1.5.11 第二通道：学员抽验记录与 G2 放行条件

**学员抽验是有产物的动作，不是口头问一句**。若只是口头请学员"抽验一下"，学员回一个字母，没有留下任何命令、输出或结论，"待人眼"的判据就会一直停在待定，却已随提交入库。

- **产物**：运行目录下的 `evidence/user-check.md`，两部分来源不同：
  - 命令与输出：检查命令可以交 `qa` 跑，同一条命令两次（正向一次、负向一次），由 `--record` 自动写进这份文件；
  - 人眼三问各一行加结论一行：**学员自己读完输出后，在同一份文件里写**。**lead 与 `qa` 不得代写这四行**，学员口述、lead 代记也不行〔本课安排，2026-11 实测；本节原先允许 lead 代记，现取消〕。
- **内容三块**：
  1. 命令与输出：本单元检查命令的正向与负向、库文件指纹前后对比，原始输出与退出码（自动写入）；
  2. 人眼三问，每问一行（全书措辞统一）：**数字对上了吗**——检查命令两次的结果和预期一致（正向绿、负向红），页面上你抽看的数字和它说的一致？**一眼看得懂吗**——不看代码、不问人，你能看懂这一页在说什么？**有没有明显错的**——错字、空白卡、乱码、和你的业务常识明显不符的数？其他"待人眼"判据，逐条写结果；
  3. 结论一行：放行 / 打回 + 退回哪一环（写明哪几条）。
- **单元三硬线**：放行 G2 之前，学员亲手在页面上点一次巡检、提交两条调价建议、批准其中一条（另一条仍是"待审"）。这一步只点页面、不碰命令行；**lead 与 `qa` 不得代点，即使学员授权也不行，学员休息时授权代办也不包括这一项**。没做，lead 不问 G2〔本课安排，2026-11 实测〕。
- **单元四硬线**：放行 G2 之前，学员亲手在 DSH 里装插件、在对话里说三句话出卡、导出卡片。这一步只点界面；**lead 与 `qa` 不得代做，即使学员授权也不行，学员休息时授权代办也不包括这一项**。没做，lead 不问 G2〔本课安排，2026-11-23 用户追加〕。
- **G2 放行条件（缺一不放行）**：
  1. `evidence/user-check.md` 存在，命令与输出两次齐全，且正向 PASS、负向变红（1.5.10），人眼三问三行与结论一行齐全、是学员本人写的；
  2. `L1-QA.md` 和规格里所有标"待人眼"的判据都已有结论（通过或不通过，不能停在"仍未给出结论"）；
  3. 单元三另须学员亲手的页面操作已做，单元四另须学员亲手装插件、说三句话出卡、导出卡片已做；
  4. G2 由学员亲口回"放行"。
- **lead 提问 G2 之前，先检查这几条**。缺任何一条（尤其缺那四行），就不问 G2，先告诉学员缺什么、怎么补；学员补完再问。不得用"先放行、之后补"的办法绕过。
- 抽验用的产品服务由 `qa` 子 agent 或用户起，lead 不起、不读截图（1.5.3）。

## 4. 门禁按形态分叉

| 环节 | A 绿地 | B 升级 | C 重构 |
|---|---|---|---|
| 施工 | 新功能按验收标准工作 | 新功能工作 **且** 既有路径不回归 | 每步可独立回滚；**禁止一次改到底** |
| 自证 | lint/test/build 全绿 | 全绿 **且** 老测试一条没删、一条没改判据 | 全绿 **且** 新旧路径双跑输出等价 |
| 验收 | 关键路径截图 | 新路径截图 + 老路径回归截图 | **外部行为零变化** + 内部指标有数字改善 |
| 交付 | 推上去 | 灰度/回滚方案在手 | 旧代码真删了，不留开关 |

**重构的验收标准必须是数字**："重复代码块 12 处→3 处""构建 48s→31s""循环依赖 5→0"。写"代码变干净了"就是自欺，测不出来就别开重构。

## 5. 介入梯度（谁拍板）

> L1 课程版下，G1/G2 的定义、提问方式、"没回怎么办"按第 1.5.5、1.5.8 节；本节的阶段组 G0–G3 属完整版（L2）。

| 阶段组 | 我可以自己拍 | **必须升级给人** |
|---|---|---|
| G0 摸底 | 怎么考古、怎么截基线 | 发现"要动的模块没人懂"、发现必须改数据模型 |
| G1 思考 | 方案内部细节 | **任何"做什么"的变化**：范围增减、验收标准变化、前提被证伪、技术栈更换 |
| G2 施工 | 文件拆分、命名、实现路径、同量级库选择 | 对外可见行为变化、API 契约变化、超出计划范围的改动、成本翻倍 |
| G3 收口 | 提交拆包、PR 描述 | 不可逆动作：commit / push / PR / 部署 / 删数据 / 退役旧代码 |

**通用成本阈值**（G1 之外都按这个）：

- 重做成本 **< 半天** → 我按推荐直接做，看板标 `⚡`，你可事后否决。
- 重做成本 **≥ 半天** → 停，看板标 `⏸`，等你。

**G1 思考阶段是例外**：不做成本判断，凡涉及"做什么"一律问。方向错了后面全废，这时候问最便宜。这也是"怕交付的不是他要的"唯一的根治点。

**提问格式固定**（不开放式问）：

```
D<n> — <一句话问题>
现状：<一两句，为什么现在要决>
A) <选项>  代价：<时间/范围/风险>
B) <选项>  代价：…
推荐 A，因为 <理由>
默认（未回即执行）：A
```

不可逆动作**没有默认继续**，必须等到明确答复。

`⚡` 是礼貌窗口：本环还有活就先干完再等，不要干等。实现用 `pwsh` 起一个 `Start-Sleep`，等待时长按讲师约定，不要阻塞整轮。

**判例优先 + 双写**：人拍板后做两件事——
1. 在 `board.json` 的 `precedents` 加一行（给人看）；
2. 同时写进 gstack 决策台账（给 `/autoplan` `/retro` 读）：先把 JSON 写进 `sprint-runs/<ts>/tmp/decision.json`，再执行 `gstack_bash(command: '~/gstack/bin/gstack-decision-log "$(cat sprint-runs/<ts>/tmp/decision.json)"')`。

payload 只认 `decision / rationale / scope / source / confidence / branch / issue`，`skill`/`tags` 不落盘；`source` 取 `user` 或 `agent`。下次同类问题先 `gstack-decision-search "<关键词>"` 查，能套用就标注"沿用既有判例"，不再打扰。

## 6. 看板（可见性的核心）

**单一数据源 `board.json`，一条命令出两份**（HTML 给人看，Markdown 给 agent 和 grep 读）。**先更新看板，再开口汇报。**

```bash
node <渔具包>/tools/gen-board.mjs <项目根>/sprint-runs/<ts>/board.json
# 产出 BOARD.html + BOARD.md 到同目录
```

`<渔具包>` = 讲师随课发放的目录（内含 `tools/gen-board.mjs` 与样例 `tools/demo/board.json`）。L1 课程版下看板与 RING 的用法按第 1.5.6 节。

每环结束：改 `board.json`（只改状态/门禁/条目，别重写整份）→ 跑上面这条 → 用 `present` 把 `BOARD.html` 发给用户 → 再汇报。

`board.json` 字段：

| 字段 | 内容 |
|---|---|
| `project` / `form` / `run` / `updated` | 项目名、形态 A/B/C、轮次、更新时间 |
| `current` | `{ ring, name, gate, elapsed, next }` |
| `rings[]` | `{ id, name, state: done\|active\|pending\|fail, gate, duration, record }` |
| `waiting[]` | `{ id, ring, question, options:[{label,cost}], recommend, reason, default }` |
| `auto[]` | `{ id, ring, decision, reason, redo }` |
| `decisions[]` | `{ id, ring, question, choice, evidence, who, vetoable }` |
| `precedents[]` | `{ id, rule, from }` |

样例见 `<渔具包>/tools/demo/board.json`。

**层 2 — DSH 任务板**：每环一个 task，`blocked_by` 串成链，GUI 里直接看进度与 owner。任务板只表达"进行到哪"，不承载决策内容（长文本进 `board.json`）。

汇报话术固定三行：
```
现在：环 <N> <环名>，门禁 <PASS/FAIL/待判>
变了：<本环新增的 ⚡/⏸ 条目，没有就写"无">
要你：<只有 ⏸ 不为空时才展开；否则写"不用你，继续">
```

**第一行必须是对看板「现在在哪」的原文复述**。引不出 = 说明没更新；引出的和实际不符，用户会立刻看见。这样看板过期从"靠自觉"变成"汇报时自证"。

**`stale`（⟳ 待重验）状态**：产品文件一改，之前 PASS 的环 5（门禁）和环 7（验收）结论就只对旧文件有效，必须标 `stale` 而不能继续显示 PASS，也不能和"进行中"混在一起。看板同时出现两个环"在跑"时，多半就是一个 `active` + 一个 `stale`——**不是并行推进，是改一次就要重验一次**。

| 角色 | agent 名 | 何时起 | 模型 | 权限 | 产物 |
|---|---|---|---|---|---|

| archaeologist | `archaeologist` | R1 | 默认 | 只读 + 写运行目录 | `SYSTEM-MAP.md` |

| planner | `planner` | 环 3 | 默认 | 只读代码 | autoplan 报告 + 任务清单 |

## 8. 派发模板

> L1 课程版下，"形态"按第 1.5.1 节填写（`A 绿地` 或 `B 升级（存档点，不跑 R1/R2）`）；本课不跑 `/autoplan` 本体（环 3 由 lead 依次跑各评审角色代替），"环境事实"里 `/autoplan` 那一条可省略；codex 一条按实际填：有就写路径，没有就写"无 codex"，Outside Voice 按 1.5.2 环 3 的条件走子 agent 或降级。

子 agent 看不到对话，prompt 必须自包含：

```
你是 <角色>，负责 <形态> 交付的第 <N> 环：<环名>。

项目根：<绝对路径>
形态：A 绿地 / B 升级 / C 重构
运行目录：<项目根>/sprint-runs/<ts>/   ← 只读；除你明确负责的文件外不许写
本环输入：<上一环产物绝对路径>
本环输出：<文件名>

必须遵守：
- 用 gstack_bash 跑 gstack 命令，workdir 设为项目根
- 所有命令带 env {"GSTACK_SESSION_KIND": "spawned"}
- 你只能改这些路径：<write_scopes>
- 不装依赖、不改 CI、不动 <禁改项>

## 环境事实（每次必带，别让 agent 重新踩坑）
- bash 必须用 Git for Windows 的 `<Git 安装目录>\bin\bash.exe`（Git for Windows 默认安装目录下的 `bin\bash.exe`）；PATH 上的 `bash` 是 WSL，会毁 `/c/` 路径
- <本机 DPR / 屏幕尺寸 / 缩放，如果要做布局验证>
- <共享浏览器是否会被别的 agent 占用；验证一律用自建 headless Chrome>
- <codex 路径：`~/.codex/.sandbox-bin/codex.exe` + 需 `GSTACK_CODEX_MODEL` 覆盖>
- <agent 不能再派子 agent：/autoplan 这类内部要派活的技能会降级>

回报格式（不要散文）：
STATUS: done | blocked | needs-context
做了什么: <2-3 条>
改了哪些文件: <绝对路径>
证据: <命令 + 关键输出 + 红/绿>
我不确定的: <需要 lead 拍的点，或 none>
```

最后一行很关键：**让子 agent 主动交回不确定性**，别让它自己猜着往前走。

**环境事实段是这轮最贵的教训**：planner 因为只看 `command -v codex` 就下结论"codex 未安装"，白降级了一整环；qa 和我都因为不知道"共享浏览器上跑 emulate 会污染用户画面"，被用户当成页面缺陷。这些不是推理能力问题，是环境事实缺失——写进 prompt 就没了。

## 10. 回退与失败

- 回退看问题性质：架构/范围 → 回 3；实现 → 回 4；验收标准缺失 → 回 2；基线不足 → 回 R2。（L1 课程版下环号按第 1.5.2 节：判据/规格问题回环 2，改完重走环 3；实现问题回环 4；范围或前提变了回 G1；没有 R2。）
- 回退必须写进 `RING-N.md` 和看板，说明"退回哪一环、为什么"。
- 子 agent 报 `BLOCKED — AskUserQuestion unavailable`：忘了传 `GSTACK_SESSION_KIND=spawned`，重派。
- 子 agent 说"完成"但门禁跑红：只认命令输出，红就是 FAIL，回退重跑。
- 同一环修两轮还不过：停手，带 `RING-N.md` 和证据找人，别硬耗。

## 12. 浏览器与截图纪律（有 UI 的项目必读）

这轮在这上面连续误判三次，用户两次以为页面坏了。

**环境纪律**

1. **验证用自建 headless Chrome**（CDP，独立 `--user-data-dir` + 独立端口，用完 kill）。**共享可见浏览器只用来出交付截图**——否则你在切视口，用户截到的每一帧都是中间态。
2. **不要在共享浏览器上留 emulation 状态**。留下来会出现"页面按模拟视口排版、塞进真实窗口被裁掉"，用户看到的是右侧被切断、卡片少一半，他会当成真缺陷。
3. **交付截图前必须确认**：`list_pages` 不显示 `Emulating viewport`，且 `innerWidth` 等于真实窗口值。

**判定纪律**

4. **布局/呈现一律用 DOM 判定**（`getBoundingClientRect` / `elementFromPoint` / `visualViewport` / ZRender display list 的 bbox），截图只作观感参考。
5. **截图捕获管道会返回旧帧**：PNG 超时重试时可能拿到视口切换前的画面，于是"DOM 全在视口内"与"截图里第 4 张卡被切断"同时成立。防法：连拍两张丢第一张，或校验两张字节哈希不同。
6. **`canvas.width` 是设备像素**，等于 `CSS 宽 × devicePixelRatio`。直接和 CSS 宽比较会假红。
7. **`emulate` 传的宽高可能被系统 DPR 除**（本机实测传 1366/768 得到 781/439）。判据按 `innerWidth` 落地值取，不信你传进去的数字。

## 13. 单一真相源清单（开环前先定死）

每个都要指定唯一归属，并在 `SPEC.md` 写死：

| 类别 | 唯一真相源 | 第二个出口的后果 |
|---|---|---|
| 数值聚合 | `aggregate` 模块 | 页面各有各的算法，改口径要双改，且互比式门禁抓不到错 |
| 舍入 | 唯一 `round` 入口 | 两层舍入吃一位：`-6.0%` 显示成 `-5.9%` |
| 百分比 / 占比 | 同一个函数产出的值 | 同一张图图例写 3.3%、扇区标签写 3.4% |
| 展示格式化 | 唯一 `format()` 出口 | 页面 DOM 与 CLI 输出不一致，验收锚点失效 |
| 门禁判据 | 一处定义，多处引用 | 两处判据强度不同，弱的那个等于没写 |

**排查手法**：去找第二个 `round` / 第二个 `toFixed` / 第二个拼接 `元|单|%` 的地方。找到就删，不要"两边都改对"。

## 14. 门禁自足性（自证环的真正任务）

自证环**不是重跑绿灯**，是回答"这个门禁本身是不是真的"。（L1 课程版下，自证并入环 5 独立验收，由 `qa`（或 `verifier`）按本节对关键判据做坏输入对照，不新增判据，按第 1.5.2 节。）

1. **每条门禁都要用坏输入证明它会红**。造突变：改错被测实现、删掉交付物、注入外链——红不了就是桩。
2. **参数传空会让检查静默空转**。实测踩过：`requiredFuncs: []` 导致"覆盖面检查"对第二个文件永远绿。凡是遍历型判据，必须验证遍历集合非空。
3. **按名字开的白名单就是洞**。判"某个值是否只出现在展示函数里"，不能用函数名前缀（`fmt|render|show`）——把累加函数命名成 `renderAccumulate` 就绕过了。要显式名单 + 函数体兜底扫描。
4. **扫源码的判据要先剥注释和字符串**，否则既漏（注释里挂个函数名就算"已接入"）又误（注释里的代码被当成违规）。
5. **"两个入口互相一致"不等于"算得对"**。必须有一条**不 import 被测实现**的独立重算路径。
6. **校验"可复现"时绝不允许覆盖被测物**，否则是永远通过的同义反复。
7. 已知绕不过去的地方要**写进 HANDOFF**，不要假装门禁完备（正则挡不住同族新写法这类）。

## 15. 交付与部署

1. **发布产物独立构建**，不要直接把仓库根推上去——`sprint-runs/`、`SPEC.md`、`HANDOFF.md` 都是内部记录，不能公开。
2. **构建脚本自带清单 + 自检**：运行时会被加载的文件必须列全（漏一个，线上动态 import 直接废），且要校验禁用内容没混入。
3. **发布后必须在真浏览器验**，不能只看 HTTP 200。这轮就出现"状态码全 200 但页面显示加载失败"。
4. **`.html` 静态托管常做 308 重定向到无扩展名路径**，要确认 query 参数在重定向后保留。
5. 记下本机工具链的坑（如 PowerShell 下 `npm` 会命中 `npm.ps1` 吞参数，要用 `npm.cmd` 绝对路径 + 参数数组）。

## 16. 复盘要产出什么

> L1 课程版下没有独立的环 9，复盘并入环 7 收尾（简版：`closer` 写 HANDOFF 与"不要再犯"清单，不跑 `retro`），按第 1.5.2 节。

环 9 不是"写点感想"，是产出**可执行的三类东西**：

1. **技能补丁**：把这次暴露的坑写回本文件对应小节（不是写在复盘里自我欣赏）
2. **判例清单**：每条一句"下次遇到 X 就做 Y"，落在看板 `precedents` 里
3. **HANDOFF 的"不要再犯"小节**：写清"看起来该改、改了反而更糟"的地方（例：不要为了对齐"四舍五入"去改 `round` 的平局方向——那会让双重舍入的 bug 隐形）

复盘时特别记：**子 agent 主动报"我修错层了""我的检查器报错了"这类自我纠正，比多写 200 行代码有价值**。要在回报格式里主动问"你不确定什么"，并把这种诚实当加分项。
