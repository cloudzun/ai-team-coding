# 单元三 负向对照夹具 `bad_ops.db`

> 这是随工具箱发给学员的坏样例：给 `u3_check.py` 做“装坏也判得出来”的对照；G2 前用它确认检查命令“装坏必判红”。

`bad_ops.db` 是一份**故意做坏的运营库**，里面有一行“已批准”的调价申请，
幅度 16.06%（772 → 896 元），越过运营手册 P-01 的单次上限 15%。
其余三行（一条合规待审调价、一条待审整改工单、一行审计）都是正常数据。

## 应得结果

**这一步由学员自己在 G2 之前、在项目外跑一条命令；不交给 builder，也不由 lead 代跑。**
先存指纹基线（只在巡检开跑之前做一次，`u3_check.py` 缺 `--before` 会判红），再一条命令跑负向演练
（端口示例写 8801，被占用就换空闲端口，命令里的端口同步换；`<运行目录>` 换成项目目录的 `sprint-runs` 下最新的那个子目录，命令把命令行、输出和退出码写进它的 `evidence\user-check.md`）：

```powershell
py -3.12 v2\lab\tools\db_fingerprint.py data\homestay.db > before.txt
py -3.12 v2\lab\tools\u3_check.py --db data\homestay.db --ops v2\lab\fixtures\u3\bad_ops.db --base http://127.0.0.1:8801 --before before.txt --record <运行目录>\evidence\user-check.md
```

`--db` 填**产品运行时实际打开的那份业务库**：存档点与按书施工的产品是 `data\homestay.db`；
若产品直接读 `kit\db\homestay.db` 就填它（两份库初始内容相同，基线可以通用）。
填错库，指纹就守不住“业务库只读”这条——写坏运行时那份也不会红。

应得：`[FAIL] 运营库：已批准调价 #1 幅度 16.06% 超过 15%（P-01）`，退出码 1（指纹与“超上限被拒”两项 PASS）。

把 `--ops` 换成你自己服务的运营库（`data\ops.db`）再跑同一行，并且已经按第 6 章**提交过两条、批准过一条**，
应得三行 PASS、退出码 0（`--db` 也要换成产品实际读的那份库，与上面一致）。

判定只应落在那条超限的“已批准”调价上：两行状态都合法（状态域口径是调价申请三值、
整改工单另有“已完成”），所以不存在“状态越域”之类的干扰。

## 运营库里还没有调价申请也判红（2026-11-21 补的判据，“零工作量能过”收紧）

运营库里**调价申请表 0 行**时，第 2 项判红，提示：

```text
[FAIL] 运营库：运营库还没有任何调价申请：先按第 6 章在页面提交两条、批准一条再跑（三表 0/0/0 行）
```

学员的 G2 步骤本来就要求先提交两条、批准一条，所以这条红只会在“还没做”时出现。
判据看的是调价申请表，而不是“三张表全 0”：检查命令的第 3 项自己会往审计写一行，
按三表全空判的话，同一条命令第二次跑就会因为审计有行而变绿，零工作量照样能过。
本夹具（`bad_ops.db`）的调价申请表有 2 行，不受这条影响，仍然只红那条 16.06% 的超限申请。

## 重新生成

```powershell
py -3.12 v2\lab\fixtures\u3\make_bad_ops.py <业务库 homestay.db 路径> v2\lab\fixtures\u3\bad_ops.db
```

生成脚本只读打开业务库，取三张写入表的 DDL 与真实当前价，再用真实价格造出越界的那一行；
房源编号不取自讲师答案里的故事房源。
